# Tasks: Protocol rule catalogue

**Input**: [spec](spec.md), [plan](plan.md), [research](research.md), [data model](data-model.md),
[rule catalogue](contracts/rule-catalogue.md), [finding format](contracts/finding-format.md),
[validation guide](quickstart.md).

**Format**: `- [ ] Txxx [P] [USn] Description with file path`. `[P]` means the task touches different files from every
unfinished task before it and can run in parallel with them. Tests are required by the constitution: every behavior
change has a regression test task. All paths are relative to the repository root.

**Stories**: US1 ids on the findings that exist today, in the views and in the session file (P1). US2 capability rules
(P1). US3 older event versions the client accepts (P2). US4 the docs page and the checks that keep the catalogue, the
fixtures and the docs equal (P2).

**Order**: Foundational, then US1, US2, US3, US4, then polish. US2 and US3 both edit `core/frames/index.ts`, so they run
one after the other. US1 is the MVP: with it, every finding has a stable id.

**Not in this list**: the server suite (#83), a docs page per rule (#85), other capability flags, severity, any
dependency or npm script. Do not edit `ROADMAP.md` or another feature's spec directory.

## Implementation strategy

1. Foundational, then US1. Stop and check: every finding has an id, the views show it, sessions round trip and 0.1.0
   sessions open. This is the MVP, and it is what the next minor's rule pages need first.
2. US2 next, because it is the new check the issue names. Then US3, which changes how frames are judged and so touches
   the reader again. Then US4.
3. Commit after each phase, as `feat:`, `test:` or `docs:` Conventional Commits. The version pull request and the
   changeset are the only release steps this change takes.
