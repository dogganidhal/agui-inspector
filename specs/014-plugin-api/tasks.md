# Tasks: Plugin API

**Input**: [spec](spec.md), [plan](plan.md), [research](research.md), [data model](data-model.md),
[plugin API contract](contracts/plugin-api.md), [declaration contract](contracts/configuration.md),
[validation guide](quickstart.md).

**Format**: `T###` is one checklist task. `[P]` means the task touches different files from the other open tasks and
can run in parallel. `[USn]` maps a task to a user story in the spec. Tests come before the code they cover, and each
test must fail first. Tests are required by the constitution and by FR-024.

**Rules for every task**: no new dependency, no new `npm run` script, no change to the content security policy, to
`hosting-config.json`, to the recorder or to the session format. Docs use short plain sentences, no em dashes and no bold
labels. Run `npm run typecheck` after each source task and `npm run test:unit -- <path>` for the tests it names. While
iterating on end-to-end tests, run `npm run test:e2e -- <path> --workers=2`.

**Stories**: US1 declare and load (P1). US2 header providers (P1). US3 run hook (P1). US4 renderers (P2). US5 failures
never stop the page (P1). US6 the command (P3). The order below follows what each story needs, not the priority: US5 is
mostly the failure paths of the loader and comes right after US1.

## Implementation strategy

   the same-origin rule and the policy proved.

   end-to-end test. US2 comes first because it holds the strictest privacy rule and gives the seam US3 reuses.

5. The example, the docs and the changeset last, then US6 when feature 005 has merged, then the full gate and the review.
   Stop at any checkpoint: each leaves the page working and the tests green.
