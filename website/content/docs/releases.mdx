This page is for maintainers. To learn what you can rely on today, read
[Project status and privacy](./status.mdx) instead.

The package name is `agui-inspector` on both npm and PyPI. The first release, Python 0.1.0, reached
[PyPI](https://pypi.org/project/agui-inspector/) on 2026-10-03. The name is still unregistered on npm.
No command in the repository publishes, tags or releases by itself. A release happens when the maintainer merges the
version pull request and approves the `pypi` and `npm` deployments. The roadmap's
[current status](https://github.com/dogganidhal/agui-inspector/blob/main/ROADMAP.md#current-status) is the one summary of where the release stands. To run
changes that are not released yet, use a source checkout, as
[Embed in Starlette or FastAPI](./embedding.mdx#working-from-a-source-checkout) describes.

## Current state

- Python 0.1.0 is published. `release.yml`, the only workflow that publishes, tagged it and uploaded the wheel
  and the sdist to PyPI with attestations. The [changelog](https://github.com/dogganidhal/agui-inspector/blob/main/packages/python/CHANGELOG.md) lists each release.
- The npm release is set up in the same workflow, but nothing is published to npm. It waits for the maintainer's
  [one-time setup](#one-time-setup-for-npm).
- The npm package and the Python package have `"license": "MIT"`. The root manifest and the Python version holder are
  `"private": true`; `packages/inspector` is not. The npm `files` list and the Python `license-files` include
  `LICENSE` and `THIRD_PARTY_NOTICES.txt` (see [Dependencies](./dependencies.mdx)), so the npm tarball, the wheel and
  the source distribution (sdist) all contain them.
- The Python package has `License-Expression: MIT` and no `Private ::` classifier, so PyPI accepts an upload. The build
  job refuses to publish if the classifier comes back.

## Gates

| Gate | Status | What it decides |
| --- | --- | --- |
| License | Closed: MIT. | `LICENSE` and the third-party notices ship in every distribution. |
| Package names | Closed: `agui-inspector` on npm and PyPI. | The name in both manifests. The first PyPI publish registered it. On npm, the maintainer registers it with a first publish by hand. |
| Upstream placement | Open. | Whether upstream accepts the inspector under `apps/inspector`, and when. `@ag-ui/inspector` applies only if upstream adopts the project. Nothing registers or reserves it. |

While a gate is open, stop and ask instead of picking a default.

## Python release

Changesets choose the version, and the workflow does the rest. The repository stores no PyPI token.

1. A pull request that changes what the Python package does or ships, including a user-visible inspector change,
   adds a [changeset](./development.mdx#changesets). Before 1.0.0, a change to a config, session, profile or plugin
   format puts its migration in the changeset line. That is how the changelog documents it.
2. On every push to `main`, `release.yml` runs `changesets/action`. With pending changesets, it opens or
   updates a `chore: version packages` pull request, which runs `scripts/changeset-version.mjs`. That script bumps
   `packages/python/package.json`, a private file that only holds the version for Changesets. It writes
   `packages/python/CHANGELOG.md`, copies the version into `pyproject.toml` and updates `uv.lock`. It accepts only
   plain `x.y.z` versions, so do not use `changeset pre`.
3. Merging the version pull request is the release. The next run tags the commit `agui-inspector-python@<version>`,
   `agui-inspector@<version>` or both, depending on which version changed, and runs the build and publish jobs.

The build job has `contents: read`. For each package the run tagged, it stops unless the commit has that package's tag.
It also stops if the `Private ::` classifier is still in `packages/python/pyproject.toml` or
`packages/inspector/package.json` is still private. It installs with `npm ci --ignore-scripts` and runs the strict gate `npm run check:ci -- --strict` on Python 3.14. Pull request CI already tested 3.10 and 3.14.
Then it builds the wheel and sdist from the checked build with `npm run package:python -- --no-build`, packs the npm
tarball with `npm pack`, and uploads the artifact of each package the run tagged. A publish job runs only for a
package that was tagged, so releasing one never publishes the other.

The publish job has `id-token: write` and uses the `pypi` environment. It runs no repository code: it downloads the
artifact and uploads it with `pypa/gh-action-pypi-publish`. That action also publishes PEP 740 attestations naming the
workflow and commit.

Only the version job can write to the repository (`contents: write`, `pull-requests: write`). It pushes tags and the
version branch, and creates no GitHub release. Every action is pinned to a full commit SHA.
`test_the_release_workflow_versions_with_changesets_and_publishes_only_through_trusted_publishing` in
`test_distribution.py` fails if the trigger widens, a token or an extra write permission appears, a second way to
publish appears, or a pin loosens. `tests/release/changeset.test.ts` fails if the version copies differ or Changesets
stops versioning either package on its own.

### One-time setup

Only the maintainer can do these. Nothing in the repository changes a setting.

1. On PyPI, add a pending publisher at [pypi.org/manage/account/publishing](https://pypi.org/manage/account/publishing/):
   project `agui-inspector`, owner `dogganidhal`, repository `agui-inspector`, workflow `release.yml`,
   environment `pypi`. The first successful publish creates the project and registers the name. The workflow was
   `release-python.yml` for 0.1.0. PyPI matches the file name, so edit the existing publisher to `release.yml` before
   the next release.
2. In the repository settings, create the `pypi` environment, add yourself as a required reviewer so every publish
   waits for approval, and limit deployment to `main`.
3. Under Settings, Actions, General, allow GitHub Actions to create and approve pull requests. Without it, the
   workflow cannot open the version pull request.
4. Before the workflow reaches `main`, tag a commit on `main` with the current version and push the tag:

   ```sh
   git tag agui-inspector-python@0.0.0 <commit> && git push origin agui-inspector-python@0.0.0
   ```

   Changesets tags any package whose current version has no tag. Without this step, the first run tags 0.0.0 and the
   build job stops at the classifier check. If that happens, delete that tag.

### Cutting a release

1. Check the gates CI cannot cover: the headed benchmark on the physical runner (see
   [Integrated-MVP gate](./development.mdx#integrated-mvp-gate)) and a manual smoke test of each distribution mode.
2. The first release removed the `Private :: Do Not Upload` classifier, in the same pull request as the `minor`
   changeset that moves the package from 0.0.0 to 0.1.0. `test_distribution.py` now checks that the classifier is
   absent, and the build job refuses to publish if it returns.
3. Merge the `chore: version packages` pull request. GitHub Actions opened it, so it does not start the pull request
   workflows, and its required checks stay pending. Close and reopen it once to run `ci.yml`.
4. Approve each deployment that waits: `pypi` for the Python package, `npm` for the npm package. When they finish, check the files and their
   attestations on [pypi.org/project/agui-inspector](https://pypi.org/project/agui-inspector/), and the provenance on
   [npmjs.com/package/agui-inspector](https://www.npmjs.com/package/agui-inspector).

You cannot replace a published version. To fix a bad release, yank it (mark it as withdrawn) on PyPI, deprecate it with
`npm deprecate` on npm, and publish the next version.

## npm release

The npm package `agui-inspector` is released by the same workflow and the same version pull request as the Python
package. It was `release-python.yml` until npm joined it. Each package has its own version and tag, and a changeset
names the packages it bumps. A release publishes only the packages whose version changed.

The publish job for npm, `publish-npm`, has `id-token: write` and uses the `npm` environment. It has no checkout. It
downloads the tarball that the build job packed and runs `npm publish npm-dist/*.tgz --provenance`. npm trusted
publishing trades the job's OIDC token for a short-lived publish token, so no npm token is stored anywhere.
`--provenance` attaches a signed statement that names the workflow and the commit. It also makes the publish fail
instead of going out without one. The tarball holds the `dist` directory that the wheel carries, and the tests compare
the two. The root manifest and the Python version holder stay `"private": true`. `@ag-ui/inspector` still waits for the
upstream placement gate.

### One-time setup for npm

npm cannot register a trusted publisher for a name that does not exist, and it has no pending publishers like PyPI.
So a placeholder version, 0.0.0, is published by hand, and every real release comes from CI. Only the maintainer can
do these steps. Do all of them before the pull request that adds this workflow reaches `main`.

1. From a checkout of that pull request, build and publish the placeholder with your own npm login. It is the only
   version without provenance:

   ```sh
   npm ci --ignore-scripts
   npm run build
   npm publish --workspace packages/inspector
   ```

2. Tag a commit so that Changesets does not tag 0.0.0 itself and try to publish it from CI:

   ```sh
   git tag agui-inspector@0.0.0 <commit> && git push origin agui-inspector@0.0.0
   ```

3. On npmjs.com, open the settings of the `agui-inspector` package and add a GitHub Actions trusted publisher:
   repository `dogganidhal/agui-inspector`, workflow `release.yml`, environment `npm`. You can also set the
   package's publishing access to require two-factor authentication and disallow tokens, so that trusted publishing is
   the only way in.
4. In the repository settings, create the `npm` environment, add yourself as a required reviewer and limit deployment
   to `main`.

The pull request that adds the npm release also adds a `minor` changeset for `agui-inspector`. After it merges,
Changesets opens a version pull request that moves the package from 0.0.0 to 0.1.0, the same version as the Python
package. Merging that pull request is the first release from CI, and the first one with provenance.

## Build provenance

Published distributions must have verifiable build provenance. For the PyPI release, provenance comes from the checks
below, the release safeguards above, and the attestations PyPI stores with each file. The checks run on a developer machine or in pull request CI. The
safeguards are the tag check, the strict gate, the minimum permissions and trusted publishing with attestations.

`npm run package:python` (`scripts/package-python.mjs`) does this, in order:

1. Checks that `packages/python/LICENSE` and `packages/python/THIRD_PARTY_NOTICES.txt` are byte-identical to the
   root files, and stops if not. `uv_build` cannot read files outside the project, so the package has committed
   copies.
2. Builds the single set of static assets into `packages/inspector/dist`, the directory that `staticAssetsPath`
   points to. `--no-build` reuses an existing build.
3. Copies it into `packages/python/src/agui_inspector/static`.
4. Writes `packages/python/src/agui_inspector/static.sha256`, one `sha256  path` line per file. It fails if the copy's
   checksums differ from the npm directory's. `--stage-only` stops here.
5. Runs `uv build --project packages/python`, which writes the wheel and sdist to `packages/python/dist`
   (`--out-dir` changes this).

Git ignores the staged copy and the checksum file, so nothing generated is committed. Then
`packages/python/tests/test_distribution.py` opens both artifacts and checks that:

- the files under `agui_inspector/static/` in the wheel and the sdist match `packages/inspector/dist` by name and
  SHA-256, and match the packaged `static.sha256`.
- the metadata has `Requires-Python: >=3.10`, a single optional `embedded` extra with Starlette, no required
  dependency, `License-Expression: MIT`, the `LICENSE` and `THIRD_PARTY_NOTICES.txt` files, no entry point, and no
  `Private ::` classifier.
- the wheel, the sdist and the npm tarball (`npm pack`) each contain `LICENSE` and `THIRD_PARTY_NOTICES.txt`,
  identical to the root files, and the notices name every runtime package in `package-lock.json`.
- the root manifest is private, the npm package is MIT with the `repository` field that npm provenance checks, and
  `dompurify` is overridden to 3.4.16 and resolves to exactly that.
- the pull request workflow runs the Python tests on 3.10 and 3.14 and has no publishing step, and the release
  workflow keeps its safeguards.
- an installed wheel serves every asset byte for byte with Node removed from `PATH` and socket connections forced to
  fail, so nothing is built or downloaded at startup.
- the package source imports no networking or process module.

A provenance statement would cover these inputs:

| Input | Where it is fixed |
| --- | --- |
| npm dependency tree, including esbuild | `package-lock.json`, installed with `npm ci --ignore-scripts` |
| Python dependency tree | `packages/python/uv.lock`, used with `--locked` |
| `dompurify` version | Root `package.json` `overrides`, resolved to 3.4.16 in `package-lock.json` |
| License and notices | `LICENSE` and `THIRD_PARTY_NOTICES.txt`, copied into both packages and compared by tests |
| Python build backend | `uv_build==0.12.22` in `packages/python/pyproject.toml` |
| `uv` version used by CI | Pinned in `.github/workflows/ci.yml` |
| Static asset content | `static.sha256`, compared with the npm directory |

Still needed: the maintainer's one-time npm setup, the first npm publish with provenance from CI, and the headed
benchmark on the physical runner. The required reviewer on the `pypi` and `npm` environments is the guard against an
accidental upload.
