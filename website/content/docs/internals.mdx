This page is for contributors who change the inspector itself. For the edit-and-preview loop and the commands, see
[Development](./development.mdx).

The code under `packages/inspector/src` has three layers:

- `core` is TypeScript with no React (a test checks this): the recorder, the frame reader, the session store,
  configuration, presets and profiles, session files, the A2UI lifecycle, the projection that expands chunk
  events, and the runtime with its guarded transport.
- `views` holds the React views (connection, conversation, inspection, A2UI and settings) and the theme's tokens and
  primitives.
- `server` is the Node-side code of the Express, Hono and Next.js helpers: one core on the web-standard `Request` and
  `Response`, a `node:http` bridge and one thin file per framework. It is not part of the page. The build compiles it to
  `packages/inspector/lib` for the npm package, and a test checks that the page bundle has none of it.
- `app` is the assembly that builds the page. `startup.ts` reads `hosting-config.json`, turns it into the transport
  policy and the content security policy, and only then creates the runtime. `index.tsx` keeps the page's state around
  one shared session store and turns each view callback into one call on a core module. `boundary.tsx` keeps a render
  failure inside the pane where it happened. `brand.tsx` draws the top bar's mark and name, or the adopter's logo and name.

The shared types are in `contracts.ts`, which imports no React either.

The connection, conversation, A2UI and settings views import no stylesheet of their own. The assembly loads
`views/theme/index.ts` and each view's CSS (`views/conversation/conversation.css`, `views/a2ui/a2ui.css`,
`views/settings/settings.css`, `views/connection/connection.css`), so a view adds no asset to the build.

## The recorder

The evidence on [Read frames and findings](./inspection.mdx) comes from three parts under [`packages/inspector/src/core`](https://github.com/dogganidhal/agui-inspector/tree/main/packages/inspector/src/core): the recorder (`recorder`), the frame reader (`frames`) and the session store (`store`).

Each preparation request, conversation run request and raw submission becomes one exchange. The recorder fills in:

| Field | Source |
| --- | --- |
| `kind`, `method`, `path`, optional run link | Given by the caller. |
| `requestBody` | The exact text sent, including whitespace and key order. |
| `requestBodyJson` | That text parsed, only when it is valid JSON. |
| `startedAt` | Wall-clock start, in epoch milliseconds. |
| `status` | The response status, once a response exists. Absent for a transport failure. |
| `responseBody` | The response text, for an ordinary response or any non-2xx response. |
| `elapsedMs` | From dispatch to the end of the exchange, on a monotonic clock. |
| `transport`, `transportError` | How the transport ended: `completed`, `transport-error` or `user-stopped`. |

An event stream does not go into `responseBody`. Its bytes go to the frame reader as they arrive, in the chunks the
network delivered. Each chunk is stamped with the milliseconds since dispatch. The recorder does not split or
interpret them.

### What the recorder never touches

The recorder reads no request or response headers. It never receives or copies a request object, so no
authentication data can enter an exchange through it. It ignores `Content-Type`: the caller says whether to expect
an event stream, so a wrong type from the server changes nothing. Apart from the body, the recorder uses only the
status. It keeps a non-2xx response to a run request as a text error body and never reads it as events.

The recorder adds two kinds of finding to an exchange:

- `transport`: the request failed before a response, or the connection failed during the stream. Its message is only
  the error's name and message.
- `capture`: the recorder's own output failed, for example because the sink threw. The recorder reports it once, the
  client still gets its response, and recording of stream chunks stops there.

A user stop gets no finding. The recorder never creates a terminal, cancellation or error event for a stopped, failed
or cut-off stream. Missing-terminal findings and observed run outcomes come from the frame reader and the store,
because they see the events.

### How the client branch stays untouched

The recorder clones each response before anything reads it, reads the clone, and gives the original to the protocol
client. The two branches read the same bytes independently, so:

- a slow client does not delay recording, and a slow recorder does not delay the client;
- if the client rejects the stream, for example for a malformed frame or a sequence violation, recording continues to
  the end of the stream;
- the client gets the response unread and unlocked, with only its line endings changed.

The runtime changes them after the recorder has cloned the response. The pinned `@ag-ui/client` cannot read lines
that end in CRLF or in a lone carriage return (CR), although both are valid in server-sent events (SSE). So before the
client reads its copy, the runtime turns each CRLF and each lone CR into one line feed (LF). Every other byte stays as
received, in the same order. The recording comes from the other branch, so its envelopes keep the server's
delimiters, and the frames list shows them. The rewrite stays until the pinned client is updated to the first release
that contains [ag-ui-protocol/ag-ui#2939](https://github.com/ag-ui-protocol/ag-ui/pull/2939) (see
[Dependencies](./dependencies.mdx#crlf-and-cr-event-streams)).

Capture ends only when the response ends, fails or is stopped, not when the call that sent the request returns or the
client stops reading the stream. The runtime gives the recorder the request's abort signal and a callback. When the signal aborts, the recorder stops reading, keeps what it already read, marks the exchange
`user-stopped` and calls the callback, even if the response body is still open. The runtime keeps the abort
controller until every recording under it has called back, so Stop works while bytes are still being recorded.

Two limits come from the platform:

- The cloned stream buffers data for the slower branch, with no size limit. The recorder reads promptly, so in
  practice the client's branch is the one that waits.
- When a connection fails or a run is aborted, the stream itself discards bytes that the platform buffered but nobody
  has read yet. The recorder keeps everything it read before then.

Browsers give each branch its own copy of a chunk. Some runtimes, such as Node 24, share one buffer between both
branches. There, a client that overwrote a chunk it had read could change what the recorder sees. The protocol client
does not do this, and the recorder does not copy chunks to protect against it.

## The frame reader

The reader decodes the bytes as streaming UTF-8 and splits them into blocks at blank lines. LF, CRLF and CR all end a
line, in any mix. A CR at the very end of a chunk waits for the next byte, in case an LF follows. A chunk boundary can
be anywhere, even inside a delimiter or a multibyte character, and the frames are the same.

Each block becomes one frame, in arrival order. Its `index` counts from zero over every frame in the exchange:

| Classification | What it is | AG-UI frame |
| --- | --- | --- |
| `data` | A block with at least one `data` field. Several `data` lines are joined with an LF. | Yes, even when the data is not JSON or not a valid event. |
| `control` | A comment (`: keepalive`), `event`, `id` or `retry` fields with no data, or a stray blank line. | No |
| `partial` | Text left when the stream ended before a closing blank line. SSE never dispatches it. | No |

Each frame keeps `envelope`, its original text with every delimiter. Joining an exchange's envelopes gives back the
decoded stream. A `data` frame also keeps `data`, the extracted value. `offsetMs` is the offset of the chunk that
carried the envelope's last character. A frame that waited for a possible LF keeps the offset of the chunk that
carried its final CR. Offsets never decrease within an exchange, and a trailing partial frame has the last chunk's
offset. In the 5,000-frame benchmark, the retained-frame count is the number of `data` frames.

The text model has two limits. Bytes that are not valid UTF-8 appear as U+FFFD in the envelope, because a string
cannot hold them. A leading byte order mark stays in the envelope, but the reader ignores it when it reads the first
field.

Control and partial frames are evidence of what the server sent. They get no event type, parsed value or verdict, and
the reader never turns them into events.

### Verdicts

For each `data` frame, the reader runs `JSON.parse`, then checks the value against the upstream `EventSchemas`. The
frame gets two verdicts, `jsonVerdict` and `schemaVerdict`, and one finding when something is wrong:

| Case | `jsonVerdict` | `schemaVerdict` | Finding |
| --- | --- | --- | --- |
| Valid event | `valid` | `valid` | None |
| Not JSON, including empty data | `invalid` | `not-applicable` | `json` |
| Object whose `type` is not one of the 31 baseline types | `valid` | `unknown-type` | `schema` |
| Known type with a wrong or missing field, or JSON that is not an object | `valid` | `invalid` | `schema` |

The reader does not check event order. In a sequence violation each event is valid on its own, so its frame has no
finding. The protocol client reports the violation, and the conversation layer adds it to the run as a `sequence`
finding. Sequence violations never stop the reader or the recorder.

When the stream ends, the reader looks for a schema-valid `RUN_FINISHED` or `RUN_ERROR` frame. If there is none, it
adds one `terminal` finding. It writes no run outcome, so the outcome stays `unknown` until something observes one.

## The session store

`createSessionStore` keeps one capture's exchanges, raw frames, runs, findings and derived entries in memory. An
append takes effect immediately. Subscribers are notified at most once per animation frame (`requestAnimationFrame`,
or a scheduler you pass in), however many appends happened in between. So a busy stream never waits for a view.

Raw frames, findings and derived entries are separate records. A finding points to a frame, run or exchange by id and
changes none of them. A derived entry, such as an expanded chunk, lists the raw frames it came from. It is labeled
`derived` and has no frame index. When its source cannot be identified, it says `ambiguous` instead of guessing. The
store keeps and updates an exchange's transport state and a run's observed outcome separately.

The store refuses a call, and changes nothing, when the call would break a rule that a later export or import depends
on: a duplicate id, a frame index that is not the next one in its exchange, an offset that goes backwards, or a
reference to something that does not exist. The recorder reports the refusal as a `capture` finding. That exchange's
reader then stops, so it does not add a misleading terminal finding as well.

`createFrameSink(store)` connects the recorder to the store. Exchange updates and findings go directly into the store.
Chunks go through a frame reader, and an exchange's reader ends before the store learns that the exchange is over.
Reader finding ids come from frame and exchange ids, so they never clash with the recorder's `finding-N` ids.

## Event views wiring

The conversation and state views in the [event reference](./event-views.mdx) come from these modules:

```tsx
import { ConversationView } from 'views/conversation/index';
import { StateView } from 'views/conversation/state';
import { publishChunkExpansions } from 'core/projection/index';
```

`ConversationView` takes `ConversationViewProps`. It has no interrupt, tool-result or composer controls: those are in
the connection lane (see [Connect and send a run](./runs.mdx)). Its optional `renderActivity(entry)` draws an
activity's content, such as an [A2UI surface](./a2ui.mdx), and the card then gets a Rendered and JSON switch.
`ConversationView` also draws the Message text control and keeps its [Markdown](./event-views.mdx#markdown) mode in its own state, which is never saved. The code is in `views/conversation/markdown.tsx`. It parses with `markdown-it` and folds the tokens into React elements, so no HTML string exists. A view mounted without the control shows plain text.
`StateView` takes `{ store }` and the same optional `threadId`.

The projection also lists every subagent lane in `model.subagents`, in the order the lanes began. The list keeps the lanes that a `MESSAGES_SNAPSHOT` took out of the transcript, and marks them `inTranscript: false`. `timelineOf(model)` in `core/projection/subagents.ts` turns that list and the run entries into the charts and rows of the [subagent timeline](./event-views.mdx#subagent-timeline). It is plain data with no React, so another view can use the same relationships. `views/conversation/lanes.tsx` draws a lane and holds the jump state between a lane and its row, and `views/conversation/timeline.tsx` draws the timeline.

`ConversationView` and `StateView` also take an optional `onReveal(target)`. The `target` is an `EvidenceTarget`: an `exchangeId` and, for a frame, a `frameId`. Without `onReveal`, run ids and frame references stay plain text. `InspectionView` takes an optional `reveal` target and applies it to its own filter and open rows. Each request must be a new object. `App` connects the three.

Both views show the thread that the assembly passes as `threadId`, even before that thread has an exchange. Without `threadId`, they show the thread of the latest conversation exchange, which is what an imported
recording needs. Both views read the store through `useSyncExternalStore` and follow its animation-frame batching.

`views/conversation/conversation.css` uses only theme tokens and defines none. Call `publishChunkExpansions(store)`
after every store change, so the frames list shows each expansion under its chunk. Its ids are stable, so it appends
only what is new. The projection reads only raw frames, without client callbacks, so it also works on an imported
[recording](./recordings.mdx).

### State history modules

The [state history](./event-views.mdx#state-history) comes from three framework-free modules in `core/projection` and the view parts in `views/conversation/state-history.tsx`:

```ts
import { applyStateDelta } from 'core/projection/patch';
import { diffStates } from 'core/projection/state-diff';
import { pointAt, pointCount, stateAfter } from 'core/projection/state-history';
```

The projection keeps its single fold of snapshots and deltas. `StateModel` gains an optional `initial`, the state the first run carried in its input. A `StateChange` can carry a `checkpoint`, the state after that change, on every 64th delta since the last snapshot or checkpoint. A checkpoint is a reference to an object the fold already made, so it costs no copy.

`applyStateDelta(state, operations)` is the one rule for a delta: it applies to an empty object when there is no state yet. The projection and the history both call it, so a past state cannot differ from the current one.

A point is an index into `model.state.changes`, which is newest first. Index 0 is the newest change and `changes.length` is the starting state, when there is one. `stateAfter(model, index)` walks to the nearest older anchor (a snapshot, a checkpoint or the starting state) and replays at most 63 deltas. `pointAt(model, index)` adds the diff against the state before the point. `diffStates(before, after)` returns the added, removed and changed paths.

`StateView` keeps its props. It keeps the selection in component state, as the key of a change or none to follow the latest, and drops it when the store or the thread changes. `StateDetail` and `selectedIndex` are pure, so a test can render any point without state.

## Waterfall wiring

The [waterfall](./inspection.mdx#waterfall) is a tab of `InspectionView`. It comes from these modules:

```ts
import { buildWaterfall } from 'core/projection/waterfall';
import { WaterfallPanel } from 'views/inspection/waterfall';
import { treeKey, visibleRows } from 'views/inspection/waterfall-model';
```

`buildWaterfall(session, threadId)` is framework-free and pure. It runs `projectConversation` over the session without its `MESSAGES_SNAPSHOT` frames and builds one group per run, newest first. A messages snapshot replaces the transcript in the projection, which would drop messages and tool calls that streamed earlier, and keeps only the subagent lanes in `ConversationModel.subagents`. A timeline has to keep all of them. Subagent rows are the projection's lanes (`SubagentEntry`): which entries a subagent run holds, which lane it sits in, its status and its offsets are the projection's facts. The builder adds one rule, that a subagent started by a tool call sits under that call's row, and it refuses a move that would put a row inside its own subtree. Each row takes its start from the first frame the projection names for the entry in its own exchange, and its end from the frame that ends it by event type. A row with no such frame has no end and is open. The frames of another exchange are ignored, because offsets count from each request.

`WaterfallPanel` is controlled. It takes the session, an optional `threadId`, the selected row, the closed rows and callbacks, and `InspectionView` holds that state. The state belongs to one store and one thread, so a new thread or an imported session starts it again. `InspectionView` takes the `threadId` as an extra prop next to `reveal`, and `App` passes the conversation's thread. A row's frame buttons and the Enter key call the same function that applies a `reveal` request, so the frames list opens the exchange and the frame and takes the focus.

`visibleRows`, `treeKey`, `axisTicks` and `rowLabel` are plain functions with no DOM. The tree follows the ARIA tree pattern with a roving `tabindex`: one row is in the tab order, and a row that gets focus is selected. Bars are positioned boxes whose `left` and `width` are percentages of the run's axis, set through the element style object. `views/inspection/waterfall.css` uses only theme tokens and defines none.

## A2UI view wiring

[A2UI surfaces](./a2ui.mdx) describes what users see. The view behind it works on its own or inside the conversation
view's activity card:

```tsx
import { A2uiView, a2uiActivity } from 'views/a2ui/index';

// Standalone
<A2uiView activityId={id} operations={content.a2ui_operations} renderEnabled={profile.renderA2ui} onAction={start} />

// Inside the conversation view's card
<ConversationView {...props} renderActivity={(entry) => a2uiActivity(entry, { renderEnabled: profile.renderA2ui, onAction: start })} />
```

`a2uiActivity` returns `undefined` for any type other than `a2ui-surface`, so the card stays on JSON. When a user
activates a control, the view calls `onAction` with the five-field action. The assembly puts the action in
`forwardedProps.a2uiAction.userAction` and starts the run. The view itself never sends a tool reply or starts a run.
Neither the view nor `core/a2ui` imports `@ag-ui/a2ui-middleware`.

`views/a2ui/a2ui.css` maps the renderer's `--a2ui-*` variables to the inspector's tokens (`--bg`, `--fg`, `--acc`,
`--line-2`, `--r-sm`, `--u`, fonts), in light and dark mode. That is why the public `--agui-*` properties restyle
surfaces. Components that the inspector draws use `agui-a2ui-*` classes from the same file. The stylesheet of
`@a2ui/react` 0.12.0 has unresolved CSS-module class names, so the inspector does not load it. Layout comes from the
renderer's inline styles, except for `Row`.

In 0.1.0 the renderer is in the main bundle. `npm run check:bundle:renderer` reports how much room is left.

## Settings view wiring

The configuration, preset and profile formats are in `packages/inspector/src/core/config`, `core/presets` and
`core/profiles`. They make no network requests of their own. The settings view takes its data and callbacks as props
(`SettingsViewProps`) and keeps no important state. The assembly supplies:

- `agents` from `parseConfig` or `loadConfig`, and `selectedAgentId`;
- `profile` from `loadProfile`, saved with `saveProfile` on every `onChangeProfile`;
- `variables`, the user's edited values, passed to `preparePreset` as overrides;
- `onImportProfile`, which calls `importProfile` and shows `error` when it fails;
- `onExportProfile`, which downloads `exportProfile(profile)`;
- optionally `capabilities`, the loaded state of a capabilities URL.

The top bar's `TargetControls` has an `agentPicker` slot for the same picker. Render the settings view's `AgentPicker`
there with the same `agents`, `selectedAgentId` and `onSelectAgent`, so a choice in either place runs the same
handler.

## Theme tokens

The tokens and primitives are in [`packages/inspector/src/views/theme`](https://github.com/dogganidhal/agui-inspector/tree/main/packages/inspector/src/views/theme). [Theming](./theming.mdx#public-properties) documents the ten public `--agui-*` properties. The derived tokens below are internal: views read them, and adopters do not override them. A view adds a token only through a change to the theme.

| Token | Value | Use |
| --- | --- | --- |
| `--bg`, `--fg`, `--acc`, `--acc-fg` | The matching public property | Short names for views |
| `--sunk` | `fg` 4% into `bg` | Code blocks, inputs, selected rows |
| `--hover` | `fg` 5.5% | Row and button hover |
| `--line`, `--line-2` | `fg` 10% and 18% | Dividers, control borders |
| `--muted`, `--faint` | `fg` 64% and 40% | Secondary text, including the conversation's frame references and offsets. `--faint` is for decoration only |
| `--acc-ink`, `--acc-soft`, `--acc-line` | Accent mixed into `fg` or `bg` | Accent text, fills, borders and focus halos |
| `--err`, `--warn`, `--ok` and `-soft` fills | `oklch()` at fixed hues 27, 70 and 150 | Findings, outcomes, status codes |
| `--f-text`, `--f-tool`, `--f-reason`, `--f-state`, `--f-activity`, `--f-neutral` | `oklch()` at hues 255, 300, 200, 75 and 350; neutral is `--muted` | Event family dots and timeline ticks |
| `--j-str`, `--j-num`, `--j-lit` | `oklch()` at hues 150, 255 and 300 | JSON highlighting |
| `--u` | `4px × --agui-density` | Spacing unit. Paddings and heights are multiples of it |
| `--r`, `--r-sm`, `--r-xs` | Radius × 1, 0.7, 0.45 | Cards, controls, tags |
| `--pop`, `--lift`, `--scrim` | Shadows and the dialog backdrop | Floating layers, raised controls |
| `--ease` | `cubic-bezier(.16, 1, .3, 1)` | Every transition |

[Theming](./theming.mdx#host-page-styles) explains where these tokens are declared (on `#root`, with their dark
variants) and why a host page's own `--bg` or `--muted` cannot reach them.

## Theme primitives

Views import the primitives from `packages/inspector/src/views/theme/index.ts`, which also loads the theme's two
stylesheets. The components take no `className`. If a view needs a variant that does not exist, add the variant to the
theme instead of overriding the primitive's styles in the view.

| Primitive | Variants and states |
| --- | --- |
| `Button` | default, `primary`, `ghost`, `small`, `iconOnly` (requires `aria-label`); hover, active, disabled |
| `Tag` | neutral, `line`, `dashed`, `accent`, `ok`, `warn`, `err`; optional `pulse` |
| `FilterChip` | default, pressed, disabled; optional family dot and count |
| `FamilyDot` | filled, `hollow`; `text`, `tool`, `reason`, `state`, `activity`, `neutral` |
| `Card`, `CardHeader`, `CardBody`, `CardFooter` | plain, `interrupt` |
| `CodeBlock` | `json` (highlighted) or `raw` (exactly as given); keyboard focusable, height at most 340 px |
| `SegmentedControl` | `aria-pressed` on each option |
| `Switch` | `role="switch"` with `aria-checked` |
| `Field`, `SearchField`, `Editor` | default, focus, `invalid` |
| `Popover` | native `popover`, placed under the button whose `popoverTarget` is its `id` |
| `Dialog` | native modal `<dialog>` controlled by `open` |
| `ToastRegion`, `useToasts` | polite live region; a toast disappears after 3.2 s |
| `Finding` | neutral, `warn`, `err`, always with an icon |
| `Label` | uppercase caption, or a `<label>` when given `htmlFor` |
| `Icon` | The 24-grid inline SVG set in `primitives.tsx`; no icon library |

Every primitive follows these rules:

- Native elements only. Focus shows as a 2 px outline in the accent at 55% opacity, offset 1 px.
- Color never shows status alone: a tag has its word, and a finding has an icon.
- `prefers-reduced-motion: reduce` turns off the pulse, the caret, the row fade and every transition. `agui-caret` and
  `agui-fresh` are the two motion utility classes that views may use.
- `CodeBlock` never changes text. The JSON tokenizer is lossless, and non-JSON stays `raw`.

## Runtime API

The runtime in [`core/runtime`](https://github.com/dogganidhal/agui-inspector/tree/main/packages/inspector/src/core/runtime) holds the state behind [Connect and send a run](./runs.mdx), with one call per control. The views in [`views/connection`](https://github.com/dogganidhal/agui-inspector/tree/main/packages/inspector/src/views/connection) take that state as props, and [`app/index.tsx`](https://github.com/dogganidhal/agui-inspector/blob/main/packages/inspector/src/app/index.tsx) connects the two.

```ts
const runtime = createRuntime({ store, policy, settings: () => ({ profile, variables }) });
const state = useSyncExternalStore(runtime.subscribe, runtime.getState);
```

| Where | Call |
| --- | --- |
| Agent picker, top bar or Settings: select an agent | `runtime.selectAgent(agent)` |
| Connection: endpoint typed by the user | `runtime.setTarget(url)` |
| Connection: token | `runtime.setAuth({ headerName, token })`, or `undefined` to clear |
| Composer: Send, quick messages, Stop, New thread | `runtime.send(text)`, `runtime.stop()`, `runtime.newThread()` |
| Replies | `draftInterrupt`, `answerInterrupt`, `draftToolResult`, `submitToolResult`, `continueRun` |
| Surface | `runtime.sendA2uiAction(action)` |
| Raw editor | `runtime.sendRaw(text)` |
| Loading configuration and capabilities | `loadConfig(url, guardedFetchText(runtime.transport))` |

When a run ends owing replies, the runtime calls `automate` from [`replies.ts`](https://github.com/dogganidhal/agui-inspector/blob/main/packages/inspector/src/core/runtime/replies.ts) with the profile as it is at that moment. `automate` answers what `interruptReply`, `interruptPayloads` and `toolResults` cover. It uses the same state changes as the calls in the table and marks each answer `automatic`. It returns the same value when it answers nothing.

The runtime then builds the continuation with the function that `continueRun` uses, and sends it through the same `dispatch`. So the run input equals the manual one.

`dispatch` is a loop. It sends the run you started, then each automatic continuation. It stops when nothing is answered, when the run was stopped, or after `AUTOMATIC_REPLY_LIMIT` (10) continuations in a row. At the limit the replies wait and `RuntimeState.notice` says so. The count lives in memory and starts again when a run you started is sent. It is not a setting.

A run that follows an automatic reply is written with `automaticReplies`. `send` and the reply calls resolve after the whole chain has ended. The tests are in [`automation.test.ts`](https://github.com/dogganidhal/agui-inspector/blob/main/packages/inspector/tests/runtime/automation.test.ts) and [`automation.spec.ts`](https://github.com/dogganidhal/agui-inspector/blob/main/tests/e2e/runtime/automation.spec.ts).

`policy` is the startup `TransportPolicy`: the mode, the page origin and the allowlist. It is fixed when the page
starts. A call that changes the agent or the endpoint returns `true` when it cleared a token, so the page can tell the
user.

`ConnectionView` is the frozen entry export. It shows the endpoint controls and the composer together. To put them in
different places, an assembly uses `TargetControls` in the top bar and `Composer` under the transcript, and puts
`RepliesView` below the transcript. `RepliesView` takes the same props as `ConversationView`, so one props object
works for both.

Pass `threadId: state.threadId` to `ConversationView` and `StateView`, so New thread empties them immediately.

## Recorder and protocol fixtures

The fixtures are deterministic and need no model or network. Each one gives the request the recorder is told about
and the response bytes in arrival order, so the same bytes go through recorder, reader and store.

[`recorder-fixtures.ts`](https://github.com/dogganidhal/agui-inspector/blob/main/examples/reference-agent/recorder-fixtures.ts) feeds the tests in [`packages/inspector/tests/recorder`](https://github.com/dogganidhal/agui-inspector/tree/main/packages/inspector/tests/recorder). They trap any header access on the request and the response, and run the protocol client through the failing streams.

| Scenario | Exercises |
| --- | --- |
| `splitStream` | A valid run with LF, CRLF and CR delimiters cut into single bytes, so boundaries fall inside delimiters and multibyte characters. |
| `lfStream` | A valid LF-only run in uneven chunks, which the protocol client can read. |
| `coalescedStream` | The same run in one chunk. |
| `errorJsonBody` | A 422 JSON error to a run request. |
| `errorTextBody` | A 503 plain-text error to a preparation, split inside a multibyte character. |

[`workload.test.ts`](https://github.com/dogganidhal/agui-inspector/blob/main/packages/inspector/tests/frames/workload.test.ts) runs the 5,000-frame fixture from [`tests/benchmarks`](https://github.com/dogganidhal/agui-inspector/tree/main/tests/benchmarks) through the recorder, the reader and the store. It checks that:

- exactly 5,000 `data` frames come out;
- each exchange's envelopes and data text match the hashes in the manifest;
- every frame's type and byte sizes match its manifest row;

## Session file tests

[`credential-echo.spec.ts`](https://github.com/dogganidhal/agui-inspector/blob/main/tests/e2e/inspection/credential-echo.spec.ts) covers both ways a credential can get near a recording: the token the inspector holds, and bytes the target sent back. A [scripted target](https://github.com/dogganidhal/agui-inspector/blob/main/examples/reference-agent/credential-echo.ts) repeats a synthetic token in one frame, with unusual spacing, non-ASCII text and `\r\n` delimiters. - The frame is identical on the clipboard and in the exported file.
- The export warning appears before the download. It says that payloads can contain an echoed credential, while

## Python package tests

| What | Command |
| --- | --- |
| Package, wheel and sdist | `npm run package:python` |
| Python tests | The commands below |
| Browser tests against the FastAPI example | `npm run test:e2e -- tests/e2e/python` |

Run the Python tests from the repository root. CI uses uv with the lockfile. With pip, an editable install in a
virtual environment works too (`--group` needs pip 25.1 or newer):

```sh tab="pip" tab-group="python-installer"
python3 -m venv .venv
source .venv/bin/activate
pip install -e "packages/python[embedded]" --group packages/python/pyproject.toml:test
python -m unittest discover -s packages/python/tests
```

```sh tab="uv" tab-group="python-installer"
uv sync --project packages/python --locked --extra embedded --group test
uv run --project packages/python python -m unittest discover -s packages/python/tests
```

`packages/python/.python-version` pins Python 3.10, the minimum version, so CI and the default local run use it. To
test another version, give it an environment of its own, so the two environments do not overwrite each other:

```sh tab="pip" tab-group="python-installer"
python3.14 -m venv .venv-3.14
source .venv-3.14/bin/activate
pip install -e "packages/python[embedded]" --group packages/python/pyproject.toml:test
python -m unittest discover -s packages/python/tests
```

```sh tab="uv" tab-group="python-installer"
UV_PROJECT_ENVIRONMENT=.venv-3.14 uv run --python 3.14 --project packages/python \
  --extra embedded --group test python -m unittest discover -s packages/python/tests
``` `test_distribution.py` and the browser tests need Node and a built
`packages/inspector/dist`. Without them, those tests fail instead of being skipped.
