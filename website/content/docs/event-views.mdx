title: Event reference
description: What each of the 31 AG-UI event types becomes in the conversation and state views, and which parts are received or derived.
---

The conversation and state views turn the 31 AG-UI event types into a transcript and a state history. They read decoded events, so a run in [protobuf](./protobuf.mdx) gives the same views as a run in server-sent events. The frames list in Inspection shows every event exactly as received ([read frames and findings](./inspection.mdx)). Find an event here to see where it appears on screen, or why a frame has no entry in the conversation.

## Received and derived

The recorder keeps raw frames: the text received, in arrival order, with its offset. These views never change them. What the views show is derived: a projection builds it from the frames that are valid events. Each entry lists the frames it came from, and computed values are marked:

- Durations of runs and steps are the closing frame's offset minus the opening frame's offset. A tooltip says "Derived from frame offsets, not received".
- Parsed tool arguments show once the call completes. Until then the raw fragments show, and stay inspectable.
- Expanded chunk events are derived entries whose source is the chunk frame. The chunk stays in the frames list, and the entry it opened has a dashed `from …_CHUNK` tag.
- The status, start and duration of a subagent lane, and every bar of the subagent timeline, come from frame offsets (see [Subagent lanes](#subagent-lanes)).
- The current state is the snapshots and deltas applied in order (see [State](#state)). The state at an earlier point, and the diff of each change, are derived from the same frames.
- The transcript is built from events, plus the messages in each run's recorded input.

Frames that are not valid events (not JSON, unknown type, failed schema) add nothing here. Their finding stays in the frames list. A valid event that refers to something that never started, such as `TEXT_MESSAGE_CONTENT` for an unknown message, gets a "Not shown" note linked to its frame. The note sits inside its run, where that frame arrived, so later runs never move it. The projection never invents the missing start.

## Events by family

Each family lists its events and what they show in the conversation. An event without an entry of its own closes or updates the entry its family opened.

### Run

- `RUN_STARTED` fills in the run header with the run id and, for a child run, the `← parent` id.
- `RUN_FINISHED` completes the header: duration, outcome tag, result, pending tool calls and interrupt count.
- `RUN_ERROR` completes it with the Error tag and the error message.

In the frames list, run events also mark run boundaries. [Runs](#runs) explains each outcome tag.

### Steps

- `STEP_STARTED` opens a collapsible group with the step name. It holds the events that arrive until the step finishes.
- `STEP_FINISHED` closes the group and gives it a duration.

The [waterfall](./inspection.mdx#waterfall) draws each step as a bar from its start to its end, with its messages and tool calls inside it.

### Text messages

- `TEXT_MESSAGE_START` opens a message.
- `TEXT_MESSAGE_CONTENT` adds a delta, the next piece of text. The message grows as deltas arrive and shows a caret while it streams. Each delta is listed under it.
- `TEXT_MESSAGE_END` closes the message.
- `TEXT_MESSAGE_CHUNK` builds the same entry, tagged `from TEXT_MESSAGE_CHUNK` (see [Chunks](#chunks)).

### Tool calls

- `TOOL_CALL_START` opens a card with the tool name, whether it is a client or server tool, and the call id.
- `TOOL_CALL_ARGS` streams argument fragments into the card.
- `TOOL_CALL_END` completes the call, and the card shows the parsed arguments.
- `TOOL_CALL_RESULT` adds the result to the card.
- `TOOL_CALL_CHUNK` builds the same card, tagged `from TOOL_CALL_CHUNK`.

### Reasoning

- `REASONING_START` and `REASONING_MESSAGE_START` open a collapsible entry, which stays expanded while it streams.
- `REASONING_MESSAGE_CONTENT` adds text to it.
- `REASONING_MESSAGE_END` and `REASONING_END` close it.
- `REASONING_MESSAGE_CHUNK` builds the same entry, tagged `from REASONING_MESSAGE_CHUNK`.
- `REASONING_ENCRYPTED_VALUE` shows a marker with the subtype, the entity id, the size in bytes and "not decoded". The marker does not show the value, and the frames list shows it raw.

### State

- `STATE_SNAPSHOT` and `STATE_DELTA` add nothing to the conversation. They appear in the state view, as points in its history (see [State history](#state-history)).

### Messages snapshot

- `MESSAGES_SNAPSHOT` shows a divider, "Transcript replaced by MESSAGES_SNAPSHOT", with added and removed counts. In the frames list, it lists the messages it added and removed. See [Message snapshots](#message-snapshots).

### Activities

- `ACTIVITY_SNAPSHOT` shows a card with the activity type and content. An `a2ui-surface` activity is drawn inside the card, and the card gets a Rendered and JSON switch (see [A2UI surfaces](./a2ui.mdx)).
- `ACTIVITY_DELTA` updates the card.

### Subagents

- `SUBAGENT_STARTED`, `SUBAGENT_FINISHED` and `SUBAGENT_ERROR` make a lane for each subagent in each run, with a line for each start, finish or error. Events that carry the subagent's `subagentRunId` go inside the lane. See [Subagent lanes](#subagent-lanes).

The [waterfall](./inspection.mdx#waterfall) shows each subagent run as a row of its run, nested under the tool call that started it, with its messages and tool calls inside it.

### Custom and raw

- `CUSTOM` shows a marker with its name and value. When a [plugin](./plugins.mdx#renderers) draws that name, it shows a card instead. See [Plugin renderers](#plugin-renderers).
- `RAW` shows a marker with its source and value.

## Plugin renderers

A [plugin](./plugins.mdx) can draw a custom event by its name and an activity by its type. The conversation then shows a card for the event or the activity. The card has the same header as before: the name or the type, a reference to the frame, and a switch between Rendered and JSON. The JSON view is the content as received, so the plugin's drawing is never the only way to read it.

An event or activity with no renderer looks as it always did. The activity type `a2ui-surface` is drawn by the A2UI view, and a plugin cannot take it. A renderer that throws leaves the JSON view in its card and gives one "Plugin" warning.

A renderer changes how the conversation shows a value. It never changes the frames list, the state view, the raw view, the derived entries or an exported session, and it receives a copy of the value. An imported recording is drawn with the same renderers.

## Replies the inspector answered

A run that carried replies lists them under Carried, as `resume · 2 answers` or `tool result · c-1`. When the inspector answered some of them from the [client profile](./runs.mdx#automatic-replies), one more item reads `automatic ·` followed by their interrupt ids and tool call ids. The tool card of an automatic result reads "Result · automatic". One you typed reads "Result · entered by you". The mark comes from the recorded run and never from the request, so a session from 0.1.0 has none.

## Markdown

By default the conversation shows message and reasoning text as plain text, exactly as received. HTML does not run and Markdown is not interpreted, so `[link](url)` and `<img>` appear as typed.

The Message text control at the top of the conversation switches between Plain text and Markdown. Markdown is a view of the same text. It changes nothing in the recording, sends no request and is not saved, so a reload starts in plain text again. While the page stays open the choice stays, through new threads, new runs and imported sessions. It works on a live run, including text that is still streaming, and on an imported session. You can reach it with the keyboard: Tab to the control and press Enter or Space.

Markdown applies to the text of messages with the role `assistant`, `user`, `system` or `developer`, and to reasoning text. These stay as they are: messages with the role `tool`, tool arguments and results, run results, activity content, `CUSTOM` and `RAW` values, the delta lists and the frames list.

What it draws:

- Paragraphs, emphasis, strong text, strikethrough and inline code.
- Headings. A heading in a message starts at level 3, so the page's own headings stay first. Levels 4 to 6 all become level 6.
- Block quotes, bullet lists, numbered lists and horizontal rules.
- Fenced and indented code blocks, without highlighting.
- Tables, with column alignment.
- Links, including link references such as `[a][r]` with `[r]: https://example.com`.

A code block or table that is wider than the pane scrolls inside its own box. The box takes keyboard focus, so the arrow keys scroll it.

Anything else shows as typed. That includes task list boxes, math, diagrams and web addresses that are not written as links. Footnotes are not supported: `[^1]: text` is read as a link reference, as CommonMark does.

Text can come from any agent, so these rules hold in Markdown mode:

- Raw HTML is never interpreted. It shows as typed text.
- Images are never loaded. An image shows as `[image: alt text]`, and nothing is requested.
- Only `http:`, `https:` and `mailto:` addresses become links. Any other address shows as text, including relative ones and `javascript:` or `data:` ones.
- A link opens only when you activate it. It opens in a new tab that cannot reach the inspector and gets no referrer. The address is printed next to the link text, so you can see where it goes.
- The page's content security policy is the same in both modes. The output holds no script, no inline style and no element that loads anything.

A message longer than 200,000 characters shows as plain text with a short note. So does a message that cannot be formatted, for example one that nests more than 200 levels deep. Other messages still format.

## Runs

Each conversation exchange gets a run header, even before its first frame. The outcome tag comes from the terminal event:

| Tag | Source |
| --- | --- |
| Streaming | No terminal event yet, and the exchange is still open |
| Finished | `RUN_FINISHED` with a success outcome, or none |
| Interrupted | `RUN_FINISHED` with an interrupt outcome |
| Cancelled | `RUN_FINISHED` with a cancelled outcome |
| Error | `RUN_ERROR` |
| Stopped by you | You stopped the exchange. This is transport status, not a protocol outcome |
| No terminal event | The stream ended without `RUN_FINISHED` or `RUN_ERROR`. No outcome is shown or made up |

If you see No terminal event, [missing terminal events](./inspection.mdx#missing-terminal-events) helps you find the cause.

A success outcome names its pending tool calls. If it names none, the pending calls are the ones the run started and never answered, as the protocol defines. Their cards show "Pending result".

A run's recorded input adds your turn to the transcript, with a line that says what it carried: resume answers, a tool result or an A2UI action. When a run sends the transcript again, messages already shown (by id) are not repeated. A result you entered for a pending call joins the original card and names the run that carried it.

## Following a reference

A run id in a run header, and each `frame #n` next to an entry, is a button. A run id shows its exchange in the frames list. A frame reference shows that frame. The references in the state view and in a "Not shown" note work the same way.

A reference finds its target by recorded ids: the exchange id and the frame id. Frame numbers restart in every exchange, so `frame #4` can exist in two exchanges. The button opens the one the entry came from. When you press it, the inspector:

- selects the Inspection pane (under 960 px wide, this is the only way to see it), its Inspection tab and the Frames view;
- opens the exchange and, for a frame, the frame's detail;
- keeps the filter if it lists the target, or clears it if it would hide the target, and shows a toast that says so;
- scrolls the target to the middle of the pane, marks it with `aria-current` and moves keyboard focus to it, so Tab continues from there.

This changes only what the page shows. It sends no request and does not change the capture, so it also works on an imported recording.

## Chunks

The inspector expands chunks the same way the protocol client does. A chunk with a new id opens a message, tool call or reasoning message. Chunks without an id continue the open one. The next explicit event of the same kind, or the end of the run, closes it. `RAW`, activity events and `SUBAGENT_STARTED` close nothing.

Each expansion is a derived entry (`derivation: chunk-expansion`) whose `sources` is the chunk frame. The closing event has no frame of its own, so its attribution is `ambiguous` and its source is the stream's last chunk. In the frames list, each chunk shows its derived expansion.

## Message snapshots

`MESSAGES_SNAPSHOT` replaces the transcript, so you can see what the snapshot did. The protocol client would merge it instead. The divider lists the messages it added and the ones it left out, with their text. Some entries stay so later deltas can find them: a message still streaming, an open step, a subagent lane that is still open or holds something still arriving, an activity the snapshot does not restate, and the run headers. A lane that has ended leaves the transcript, and its row stays on the [subagent timeline](#subagent-timeline).

## Subagent lanes

A run can start subagents. Each subagent gets a lane in the conversation, one lane for each subagent in each run. The lane holds what the subagent produced: its messages, reasoning, tool calls, steps, activities and custom and raw events, in the order they arrived. An event belongs to a lane when it carries that subagent's `subagentRunId`. An event without one stays in the main flow, even while a lane is open. Subagents that run in parallel get separate lanes, so their events never mix.

A subagent that another subagent starts (`parentSubagentRunId`) sits inside the lane of its parent. Lanes nest to any depth. A lane sits where its start event arrived: in the main flow, in the step that was open, or in its parent's lane. The conversation groups work by subagent, so it does not show strict arrival order. The frames list shows arrival order, and the timeline shows how subagents overlap.

State events carry a `subagentRunId` too, but they are not in the conversation, so they are not in lanes. Whole messages in a run's input or in a `MESSAGES_SNAPSHOT` stay where they were in 0.1.0.

The lane header shows the name, the invocation id, the description and the status. It also shows the start offset, the duration, the tool call and message that started the subagent, and how many messages, tool calls and subagents the lane holds directly. The start offset and the duration are derived from frame offsets. Select the header to collapse the lane or open it again. A new lane is open. A collapsed lane keeps its status and its counts. Its body starts with the lifecycle lines, each with a frame reference, and then the entries.

### Status

The latest lifecycle line of the subagent in that run decides its status. Each status has its own word and its own glyph, so you can tell them apart without color.

| Status | Glyph | Meaning |
| --- | --- | --- |
| Running | `▸` | No end event yet, the run has no terminal event, and the exchange is still open |
| Finished | `✓` | `SUBAGENT_FINISHED` with a success outcome, or none |
| Suspended | `‖` | `SUBAGENT_FINISHED` with a suspended outcome. It lists the interrupt ids when the event names them |
| Error | `✕` | `SUBAGENT_ERROR`, with its message and code. The run keeps its own outcome |
| Stopped by you | `■` | You stopped the exchange before an end event |
| No end event | `?` | The stream or the run ended without an end event for it. No outcome is made up |

A failed subagent does not fail its run. If a run ends with `RUN_ERROR` while a subagent is open, the subagent shows No end event, and the run header shows the error.

Some streams have gaps, and the lane says so:

- Events that carry a `subagentRunId` with no `SUBAGENT_STARTED` make a lane tagged "Start not received". It has no name, description or start offset.
- A subagent whose parent has no lane in the same run sits under the run, tagged "Parent … not seen in this run".
- A run that continues a subagent an earlier run suspended gets its own lane for it, tagged "Continued".
- A lane that has only lifecycle lines says "No events in this lane."

## Subagent timeline

When a thread has subagents, a "Subagent timeline" shows above the transcript. It has one chart for each run that has subagents. A chart has a time axis, a row for the run, and a row for each subagent lane, with nested subagents under their parent. Each bar starts at the offset of the frame that started the subagent and ends at the offset of the frame that ended it. A subagent that has not ended runs to the last frame of the exchange. Parallel subagents overlap on the axis.

The axis starts at the request, as the offsets in the frames list do, and ends where the frames list's ticks end. Each run has its own axis, because each request has its own clock. The positions and durations come from the offsets at which frames arrived. The optional `timestamp` of an event is not used.

Each status also has its own bar end. Running has an open end, Finished and Error are solid bars, Suspended is a dashed outline, and Stopped by you and No end event are dotted outlines. The glyph from the table above sits at the end of the bar. A chart shows its first 100 subagent rows, and a button shows the rest.

The timeline is open when it first shows, and you can collapse it. A chart that is wider than the pane scrolls inside its own box.

### Jump between a lane and its row

A row is a button. Select it to jump to its lane. The conversation opens any lane or step that hides it, scrolls to it and puts keyboard focus on the lane header. A lane's "Show in timeline" button does the reverse: it opens the timeline, shows the whole chart if the row is past the first 100, and puts focus on the row.

A lane that a `MESSAGES_SNAPSHOT` took out of the transcript keeps its row, which says "Replaced transcript". Selecting that row shows the subagent's start frame in the frames list. This follows [Following a reference](#following-a-reference).

### Keys

The rows of the timeline are one tab stop. Press Tab to move focus to them, then use these keys:

| Key | Action |
| --- | --- |
| Down arrow | Next row, across charts |
| Up arrow | Previous row |
| Home | First row |
| End | Last row |
| Enter or Space | Jump to the lane of the row |

A lane header is a button. Enter or Space collapses or opens the lane. Tab then reaches "Show in timeline" and the frame references. The arrow keys act only while a row has focus, so the message box keeps its keys. A screen reader reads each row and lane header with the subagent's name and id, its status, its duration, its start and what it is nested under.

### Subagents on a live run and in a recording

On a live run, a lane and a row appear when the subagent starts, and a running bar grows with every frame. When the end event arrives, the status and the bar change. A lane you collapsed stays collapsed.

An imported recording shows the same lanes and the same timeline as the live capture did. They need no extra field in the file, so recordings from 0.1.0 work too. Using lanes and the timeline sends no request, writes nothing to browser storage and does not change the recording.

## State

The current state is what the next run carries. It starts from the first run's recorded input state. Then each `STATE_SNAPSHOT` (replace) and `STATE_DELTA` (JSON Patch, RFC 6902) applies in order. A delta that cannot be applied shows as "not applied" with the reason. The state keeps its last valid value, and the frame stays in the frames list.

The state view shows the current state at the top. Under it, a history lists every snapshot and delta of the thread, so you can see how the state got there.

A new thread starts from its own state. Earlier exchanges leave the current conversation but stay in the session. Both views show the current thread, even before it has an exchange. An imported recording has no live thread, so the views show the thread of its latest conversation exchange. The views read only raw frames, so a recording shows the same conversation and state as the live capture did.

### State history

The history lists the changes newest first. Each row shows the offset, the event type, the run, the frame number and a short summary. For a delta, the summary is its first operation and how many more it has. For a snapshot, it is "Replaced the state". If the first run sent an input state, the history ends with a row for that starting state. A thread that has a starting state but no state event has no history to show.

Each row is a point. Select a point to see:

- the full state after that change;
- the diff, which is what the change did to the state;
- the operations the change carried, for a delta.

The newest point is selected by default. It is the current state and keeps the label "Current state". When you select an older point, a banner says "Past state" and tells you how many newer changes there are. A past state is not what the next run carries. "Back to latest" returns to the current state.

The inspector builds each past state from the recorded frames with the same rules as the current state. It never stores them, and it says that they are derived. The frame number in the label is a button that shows the frame in the frames list.

### Read a diff

The diff compares the state before the change with the state after it. Each line is one path:

- `+ added` is a new path, with its value.
- `- removed` is a path that is gone, with its value.
- `~ changed` is a path with a new value. It shows the old value and the new one.

The word and the sign tell you the kind of each line. The colored stripe next to it only repeats it. Paths are JSON Pointers, the same as in the operations. The root of the state shows as `(root)`.

The diff shows the net effect on the state. The operations are listed apart from it. A `move` shows as a removed path and an added path. A `copy` shows as an added path. A `replace` with the same value, and a `test`, change nothing, so the diff says "No net change." Two objects with the same members in a different order are equal. Arrays are compared by position, as JSON Patch counts them. If a delta removes the first item of a list, the items after it show as changed and the last one shows as removed.

A snapshot is compared with the state before it. A first snapshot with no earlier state shows in full as "First state of the thread" and has no diff. A delta that cannot be applied has an empty diff, because the state did not change.

A value longer than 80 characters is shortened. Open it to read the whole value. A diff with more than 100 lines shows the first 100 and a button for the rest.

### Move through the history

The history is one list with one tab stop. Press Tab to move focus to it, then use these keys:

| Key | Action |
| --- | --- |
| Down arrow | Select the next older point |
| Up arrow | Select the next newer point |
| Home | Select the newest point, which is the current state |
| End | Select the oldest point |

The selected point scrolls into view, and a screen reader announces each point as you move. Arrow keys act only while the list has focus, so the message box keeps its keys. "Back to latest", the frame number, the operations, the long values and "Show more" are controls that Tab reaches and Enter or Space opens. After "Back to latest", focus goes to the list.

### Live runs and imported recordings

On a live run, the newest point follows the stream. A new change appears at the top, and the state and the diff update without any action. If you select an older point, it stays selected. Its state and diff do not change while new changes arrive. The banner counts the newer changes, and "Back to latest" jumps to the current state.

The selection is not kept when you leave the State tab, start a new thread or import a recording. The history then starts at the newest point again.

An imported recording shows the same history as the live capture did. The history needs no extra field in the file, so recordings from 0.1.0 work too. Browsing the history sends no request, writes nothing to browser storage and does not change the recording. An export is the same before and after.

A past state of a very large state, after thousands of deltas, can take a moment to build, because each delta copies the state.
